Exact optimization strategy — 2026-09-20
========================================

The best next experiments are to activate existing pixel-parallel GVF execution, remove repeated visibility decoding, and reuse computations whose complete inputs are unchanged. These are concrete opportunities in the current source, not demonstrated speedups. Prioritize geometry construction separately from repeated simulation; a warm-run improvement cannot satisfy a geometry-cold claim.

This is a strategy review requested after the execution goal was stopped. No production code, numerical policy, milestone status, or benchmark protocol is changed by this document. No new numerical or performance experiment was run. Two bounded source audits informed the draft; a separate skeptical review checks the resulting proposal. [Review provenance](../reports/characterization/exact_optimization_strategy_v1/review.json) records the inspected source/evidence hashes and verification scope.

The optimization baseline is the integrated `solweig-portable-sleef-5a1d179d-v1` implementation. The nine files listed in its [promotion record](../reports/characterization/p8_portable_profile_v1/integration/promotion.json) were checked against their recorded post-integration hashes and match. Existing large admission runs precede the final fallback repair; they are not executions of the final source. The [portable-profile policy](portable_math_profile.md) and approved [scientific exceptions](../reports/scientific_release_exceptions.json) remain in force.

**What “identical” means for this strategy.** Mathematical equality over real numbers does not imply identical floating-point results. Reassociation and multiply/add contraction can change rounding; this distinction is explicit in the [LLVM floating-point specification](https://llvm.org/docs/LangRef.html#fast-math-flags) and [Numba performance documentation](https://numba.readthedocs.io/en/stable/user/performance-tips.html#fastmath). Neither source supplies a speed forecast for this project.

For new optimizations, propose a stronger candidate-to-candidate gate: preserve finite value bits, including signed zero; preserve NaN/positive-infinity/negative-infinity masks, categorical results, sentinels, all carried state, and artifact semantics. Check NaN payload bits when manipulating raw encoded payloads. Compare against a frozen current candidate on the same host/runtime/profile, then retain all existing original-reference gates. This is not a claim that the current implementation is bit-identical to every upstream math backend, nor a change to its existing tolerance policy.

Each proof must name its domain, input mutability, dtype, scalar promotion, intermediate rounding, branch order, and observable failures. Preserve existing explicit SLEEF FMA operations; do not introduce additional contraction, reassociation, approximate transcendental dispatch, or parallel reductions. For elementwise parallelism, prove that each pixel has an exclusive output and follows its original operation sequence. For stateful execution, equal state at step t plus the same transition establishes equal state at t+1; timesteps therefore remain sequential. Finite tests can falsify a proof but cannot establish universal equivalence. Unsupported domains retain the unchanged path.

**What the retained evidence establishes.** The [historical full-pipeline profile](../reports/characterization/p7_full_profile_repeated256_v2/profile/worker_functions.json) reports 4.637 seconds of self-time in `_gather_serial`, 1.803 seconds in `_decode`, and 0.209 seconds in `_utci_uniform_serial`. Its compilation and cumulative times overlap, it predates the final profile, and it used an instrumented one-thread 256-square run. These values identify leads; they are not current stage fractions or a performance baseline. In particular, UTCI should not receive priority merely because a parallel implementation is available.

The [experiment register](p7_experiments.md) retains stronger counterevidence:

**Ranked work packages.** Ranking reflects source evidence, scope, and proof cost. E0 can change the order before any performance-selection protocol is frozen.

**E0 — establish the actual limiting cost.** Freeze current source hashes, installed wheels, fixture identities, environment, requested outputs, CPU budget, and the four existing first-use/compiled geometry-cold/geometry-warm/kernel regimes. First requalify the final integrated source on required dense and vegetation admissions. Collect non-overlapping stage timers for startup/JIT, input identity/read, geometry, shadow, GVF, radiation, comfort, checkpoint/hash/flush, and export. Record allocation/workspace sizes and measured RSS, not just Python allocation counts. Use profiling only to explain a separately measured uninstrumented workload.

For a stage occupying fraction f of baseline elapsed time, acceleration s can at most produce `1 / ((1 - f) + f / s)` overall under an otherwise unchanged serial decomposition. This is a planning bound, not a forecast; contention and added work can reduce the result. Do not insert old cProfile cumulative times into this formula. A reusable computation with construction cost B and per-step saving d pays back only when `steps * d > B`, including cache load, validation, and memory effects.

**E1 — use existing independent-pixel execution.** [engine.py](../src/solweig_light/radiation/engine.py):1732 imports the serial `gvf_2018a`. [ground_view.py](../src/solweig_light/radiation/ground_view.py):133–138 already has a pixel-owned parallel gather; its serial and parallel wrappers are at 365–369. Dispatch that existing kernel under the runtime CPU budget while keeping the 18-direction loop and every pixel's ray-step sequence unchanged. This requires no new mathematical algorithm or persistent raster cache.

Start with serial versus 1/2/4-thread GVF on identical immutable inputs, comparing all returned fields and mutated `Tg`, then full chronological execution. Existing [GVF tests](../tests/differential/test_ground_view_compiled.py) cover several thread counts, but this review did not rerun them or establish final-source pipeline performance. Include NaN/minimum semantics, aliases, water cells, simultaneous tile workers, and maximum live memory. Choose a serial/parallel size threshold using separate tuning fixtures, then freeze it before evaluation.

Secondary dispatch gaps exist at [pipeline.py](../src/solweig_light/pipeline.py):268 (`utci_calculator_uniform` defaults to serial) and [engine.py](../src/solweig_light/radiation/engine.py):1720/1727 (wall kernels explicitly serial). Evaluate them separately after E0; do not imply three independent speedups will multiply. Wall kernels currently lack persistent compilation caches, and their serial variants wrap the same Python functions: adding `cache=True` naively would repeat the previous dispatcher-cache collision. Any cache work needs distinct definitions and fresh-process serial/parallel order tests.

**E2 — eliminate repeated decoding before redesigning arithmetic.** [patch_radiation.py](../src/solweig_light/radiation/patch_radiation.py):318 decodes `shmat`, `vegshmat`, `vbshvegshmat`, and `diffsh`; [visibility_compiled.py](../src/solweig_light/geometry/visibility_compiled.py):48–51 decodes shadow and vegetation again for `diffsh`. In the pipeline's known case, derive that difference from already decoded, unchanged shadow/vegetation values, with exactly the three float32 operations at 42–44. Admit reuse only for the exact known `LazyDiffVisibility` implementation whose leaves are the same immutable `shmat` and `vegshmat` objects, under their owner locks. The low-level API accepts an independent `diffsh`, including dense arrays and duck types; those retain independent decoding. Preserve the original shadow matrix: `_diff` currently mutates its first argument. In the admitted case this reduces five leaf decodes to three in that shortwave block, not the whole simulation by 40%.

Next compare a serial decoder embedded in the existing ordered pixel/patch reduction with the materialized-block path. Decode binary, ternary, and raw modes exactly; do not convert nonbinary values to Boolean. Preserve raw payload bits, patch order, mapped-owner locks and lifetime, and reserved-code failures. Avoid exceptions escaping from a parallel region by preserving validated input/error behavior before launch. Keep shortwave and the two longwave sweeps and their accumulation order distinct.

The default block size is 128. At 1024-square there are 8,192 block iterations per sweep; larger blocks or compiled outer scheduling might reduce Python calls and tiny parallel launches. Test a small predeclared block/thread grid, including the existing 128 setting, under the memory planner. Four decoded float32 blocks require `16 * pixels_per_block * patches` bytes before masks and other scratch; concurrency multiplies scratch. Do not decode an entire pixel-by-patch history to avoid dispatch costs.

[engine.py](../src/solweig_light/radiation/engine.py):1561–1564 also traverses `diffsh` for ordered `aniLum`. A later subexperiment may add an independent accumulator to the shortwave traversal and move its consumers only after proving no intervening state, exception, or data dependency is changed. This is a separate integration step; the initial decode fix need not move pipeline stages.

Smallest discriminator: bitwise block/reduction comparisons across binary/ternary/raw payloads, irregular final blocks, read-only/mapped inputs, nonfinite values, and 1/multiple threads. Include an intentionally independent dense `diffsh` and a lazy instance with different leaves to prove correct fallback. Then measure paired full-day elapsed time including setup. Stop if decoding is a minor current cost or descriptor/branch overhead erases the saving.

**E3 — reuse identical inputs at their correct lifetime.** Split this into independent changes:

- In one GVF call, compute aspect radians, fixed search-distance conversion, albedo products, and other proven direction-invariant sources once. [ground_view.py](../src/solweig_light/radiation/ground_view.py):141–150 currently copies six sources and a wall field per direction; 211–230 rebuilds source fields, and 319 reconverts aspect. Preserve snapshot ownership. In the water case, the first `Lup` is formed before `Tg` mutation at 216–219; later directions see the mutated field. A single precomputed `Lup` is therefore wrong. Preserve the first/later distinction and postprocessing's mutated `Tg`, including alias behavior, or retain the original path.
- The five total/cardinal unshadowed-albedo GVF fields are candidates for tile-lifetime reuse: their accumulators at 103/111 and 257–265 depend on fixed buildings, albedo, ray geometry/distances and related static configuration. Derive the full dependency graph before removing dynamic work. Preserve the original ray and direction reduction order when building them. Five float32 maps cost `20 * N` bytes, approximately 20 MiB at 1024-square or 247 MiB at 3600-square, plus construction peak. No reuse across mutable public calls or mismatched tile identities.
- `tan32(asvf)` in [patch_radiation.py](../src/solweig_light/radiation/patch_radiation.py):156 is geometry-derived but recomputed across timesteps. One float32 cache costs `4 * N` bytes. Preserve the exact block partition/layout for the NumPy fallback, or restrict reuse to the already admitted finite SLEEF fast domain and retain the original fallback calls. Do not replace the versioned helper with a different tangent. `atan`, solar coefficients and classifications remain dynamic. Equal ASVF values do not prove cross-profile coefficient equivalence.

For each subexperiment, compare intermediate fields and every chronological state, perturb each declared dependency to ensure invalidation, and record build time, first step, later steps and peak memory. Compute no full cached sun/shade cube without a measured, byte-bounded justification. A read-only view of externally mutable storage is insufficient ownership.

**E4 — reduce geometry construction passes.** [sky_compiled.py](../src/solweig_light/geometry/sky_compiled.py):338 allocates three patch output planes; [svf.py](../src/solweig_light/geometry/svf.py):132–143 then encodes them and repeatedly weights their masks into 15 fields. Reuse owned O(N) workspaces and precompute the exact scalar weight sequence, then consume each completed patch without changing patch→annulus→contribution order. Multiplication and addition remain separate with their original casts; do not replace repeated additions with a summed weight. Confirm that the visibility builder has captured bytes before overwriting a mask buffer.

Begin with reusable allocation and exact scalar preparation before fusing all updates. Preserve the positive-bush fallback, directional corrections, clipping, raw/nonfinite channels, all 19 returned values, NPZ/ZIP schemas, and output ownership. Compare every field by bits on adversarial small geometry, then geometry-cold full workloads. Include construction and required exports in the measured result. A warm-cache result provides no evidence for this change.

**E5 — prove a bound before skipping a sample.** The rejected [Python hierarchy](../tools/experiments/p7_hierarchical_skip.py):44–55 is useful evidence for an approach, not a production implementation. A packed compiled hierarchy could remove its Python node/query overhead, but the branch and memory costs remain unknown.

For a building-only segment with in-domain samples, let `M` bound their source heights and `d_min` be the minimum of their exact stored decrements. Under the fixed supported rounding/dtype semantics, `U_valid = round(M - d_min)` bounds each in-domain `round(source - decrement)` by monotonicity. For `exact_13`, the operative bound is `U = U_valid` when every sample is in-domain, `U = max(U_valid, +0.0f)` when the segment also contains outside-domain samples, and `U = +0.0f` when all samples are outside. A segment containing no steps requires no update. Only if this complete `U < current_horizon` can it be skipped. A negative in-domain bound alone cannot justify skipping a border's zero update. Other kernels require their own border semantics. Reject/fall back for nonfinite inputs, unsupported rounding/overflow cases, or incomplete bounds. Do not reassociate the ray arithmetic into a different threshold test.

Use strict `<` initially. [sky_compiled.py](../src/solweig_light/geometry/sky_compiled.py):71–75 selects the right operand on equality, whereas [wall_shadows.py](../src/solweig_light/radiation/wall_shadows.py):70–73 selects the left; a generic `<=` proof must account for signed-zero ties. The retained prototype tested a narrower finite domain. Compare the complete target-kernel outputs, not just a hand-written horizon model.

Start with `exact_13`; any sky specialization needs a separate all-output proof. This has limited immediate pipeline value: [pipeline.py](../src/solweig_light/pipeline.py):229 currently selects `usevegdem=1`. Equivalence of a no-vegetation specialization of that actual path must be established before crediting it with end-to-end savings. Building maxima alone do not justify skipping `exact_23` canopy/trunk/bush/wall updates. Compare flat hierarchy versus exhaustive compiled traversal, count all queries and visits, and include O(N) construction/storage. Abandon the experiment if the proven scope is rarely exercised or amortization fails.

**Lower-priority options require evidence first.** Exact immutable ray-plan reuse is worth a duplicate-key census, but GVF already caches its addressing schedules. Keep sky and wall schedule families separate, include exact scalar dtype/bits and termination in keys, and use O(ray_length) plans rather than O(pixels × ray_length) address tables. Complete shadow-result memoization requires identical geometry, scalar values, and configuration; similar angles or a repeated clock hour are insufficient. Interning identical encoded visibility payloads requires measured duplicate counts and a versioned native-cache/legacy-export design. Persistent tile workers may save imports/JIT loading on many small tiles but need explicit state reset and memory retirement. SIMD across independent pixels is compatible in principle; a new C++/Cython backend is justified only if measured generated-code limitations survive simpler changes.

Checkpoint I/O and repeated input hashing must be measured, but removing content verification, readback, `fsync`, or changing checkpoint frequency would alter robustness guarantees. Such changes are not counted as exact default optimizations here. A larger CPU budget or more simultaneous jobs is not an equal-resource single-run speedup.

**Execution and acceptance sequence.** This strategy is a proposal; a review-ready executable protocol must be frozen before measurements select a winner.

1. Finish E0. Retain original upstream references separately; never generate a new original golden from the candidate. Record current environment and raw stage attribution. Select a bounded tuning set and a separate evaluation set before inspecting candidate performance.
2. After freezing the baseline, develop E1/GVF and E2/decode independently in isolated snapshots. They own different numerical files; one integrator owns any shared engine/pipeline wiring. Run each experiment's proof checks and targeted component tests first. Only one timed job uses a host at a time; source work can proceed in parallel elsewhere.
3. Each surviving change passes exact candidate-to-candidate intermediate/state/artifact comparisons plus unchanged upstream gates. Include small/256/1024 dense, sparse and vegetation scenes, day/night, block/thread variants, out-of-domain fallback, restart and installed-wheel execution appropriate to its scope. Compile with the fixed math profile and inspect relevant generated operations; decorators alone are not proof.
4. Evaluate randomized paired fresh-process trials, normally at least five per group; predeclare and justify fewer for expensive large runs. Match geometry and compiled-cache state, all outputs, CPU allocation and checkpoint policy. Record both source snapshots, raw failures, median/uncertainty, startup, build cost and process-tree RSS. Keep the existing 12 GiB cap and 20 ms sampled summed-RSS accounting and its limitations. Final release coverage still follows plan §11, including 2048/default-3600 or predeclared memory-limited cases.
5. Define meaningful benefit and priority-workload regression thresholds in the executable protocol before comparison. An inconclusive result remains unselected; do not add trials selectively until it wins. Integrate one change, verify it, then reprofile before E3/E4. E5 needs a separate proof and crossover review. Do not sum individual speedups.
6. Compare the final combined source with the strongest documented original SLEEF CPU baseline on matched M1 hardware for release claims. Keep original Cura/MKL and original/patched CUDA categories distinct. Existing 2× cold, 3× warm and 4× memory goals remain unproven for this source; this strategy supplies no replacement measurements.

For future long runs, give Luna one host/protocol/cleanup packet and use completion or blocker reports only. A Cura owner records a unique task directory, preserves and hash-verifies evidence locally, stops only its own processes, and then removes only its task-owned remote files. Review findings and compact manifests return to the lead; routine monitoring stays with the worker. No remote workspace or benchmark was started for this review.
